A Linux machine that stays on, Docker with Compose and the server’s IP address.

You don’t need to install Docker separately.

On Synology, Docker comes as the Container Manager package from the Package Center. It already contains both the Docker engine and running from docker-compose.yml (the “Project” section). Nothing has to be installed over SSH.

Is the model suitable

Open Control Panel → Info Center → General and look at the “CPU” line.

  • Intel or AMD (the + and xs series, for example DS220+, DS923+, DS1621+) — suitable.
  • ARM (Realtek, for example DS223, DS124, DS223j) — Container Manager is not available on every ARM model. If it is in the Package Center, Vartovyi will run too: the image is built for amd64 and arm64.
  • If Container Manager is not in the Package Center, the model doesn’t support it, and Vartovyi won’t run on this NAS.

Install the packages

  1. Container Manager. On first launch it offers to create the docker shared folder — accept.
  2. Download Station. Vartovyi adds torrents through it. Not needed if you use qBittorrent or Transmission (step 4).
  3. Plex Media Server, if it isn’t installed yet. Sign in to your plex.tv account in it.

You will need the local IP address of the NAS, below <NAS_IP>, for example 192.168.1.10. It is in Control Panel → Network → Network Interface. Better reserve it in the router so it doesn’t change.

What you need

  • A 64-bit Linux machine that stays on: a mini PC, a home server, a NAS without DSM or a Raspberry Pi 3, 4 or 5. Any distribution Docker runs on will do: Debian, Ubuntu, Raspberry Pi OS, Fedora and others.
  • Plex Media Server, signed in to your plex.tv account. Plex must see the same files Vartovyi downloads: the simplest is Plex on the same machine (installed on it, or in Docker with /srv/media mounted under the same path). Plex on another machine in the same network works too: share /srv/media over SMB or NFS and add the shared folder to Plex libraries (step 4).
  • A fixed local IP address of the machine, below <NAS_IP>, for example 192.168.1.10. The command hostname -I shows it (the first address). Reserve it in the router (DHCP reservation) so it doesn’t change.
  • A terminal on the machine: a keyboard and a screen, or SSH from your computer: ssh <user>@<NAS_IP>. All commands below are run there as your usual user, not as root.

Install Docker

Vartovyi runs in Docker with Docker Compose. First check whether they are already installed:

docker compose version

If it prints a version (for example Docker Compose version v2.29.1), skip to the check. Otherwise install Docker with the official script and allow your user to run it without sudo. The first line installs curl, which minimal images may lack; it is for Debian, Ubuntu and Raspberry Pi OS (on Fedora: sudo dnf install -y curl):

sudo apt update && sudo apt install -y curl
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
sudo usermod -aG docker $USER

Log out and back in (or close SSH and connect again) so the new group applies, then run docker compose version again. If it says permission denied about docker.sock, the group hasn’t applied yet: log out once more or reboot (sudo reboot).

Raspberry Pi

  • A 64-bit OS is required. Raspberry Pi OS (64-bit), the Lite version is enough. Check with the two commands below: the first must print aarch64, the second arm64. armv7l or armhf means a 32-bit system (a 32-bit Raspberry Pi OS on a Pi 4 or 5 runs a 64-bit kernel, so uname -m alone can say aarch64; dpkg shows the system itself) — Vartovyi doesn’t run on it; reinstall a 64-bit OS with Raspberry Pi Imager.
  • A USB SSD instead of the SD card for the Vartovyi folder and the media: the SQLite database and torrents wear out SD cards quickly. The simplest is to write the OS straight to the SSD with Raspberry Pi Imager and boot from it (Pi 4 and Pi 5 boot from USB out of the box): then the default folders ~/vartovyi and /srv/media are on the SSD already. If the system stays on the SD card and the SSD is mounted, for example, at /mnt/ssd, enter /mnt/ssd/vartovyi and /mnt/ssd/media in “Your details”.
  • The SSD in ext4. Writing the OS to the SSD (above) formats it as ext4 already. A separately mounted SSD must be ext4 too: exFAT and NTFS don’t keep Linux owners, so chown fails (“Operation not permitted”) or changes nothing, and downloads stall. Reformat it as ext4 (this erases the disk); if it must stay exFAT or NTFS, mount it with the options uid=1000,gid=1000 (in /etc/fstab).
  • The official power supply (Pi 4: 5V 3A, Pi 5: 5V 5A) and a case with cooling: with a weak power supply the SSD drops out, and an overheating Pi slows itself down (throttling), and downloads slow down with it.
uname -m
dpkg --print-architecture

3Telegram

A bot that will send messages about new episodes.

  1. Create a bot. Send @BotFather the /newbot command, set a name and a username. The reply contains a token like 123456789:AAF….
  2. Find out your chat_id. Write to @userinfobot, it replies with the Id number. The bot will only respond to this chat_id.
  3. A group chat instead of your own? Then every member sees the buttons (“Download”, “Yes, delete for good”), so in a group the bot obeys only the people listed in Allowed user IDs (TELEGRAM_ALLOWED_USER_IDS, user ids from @userinfobot separated by commas); with the list empty it obeys nobody there. In a personal chat the list isn’t needed.
  4. Open your bot and press Start. Without this the bot cannot write to you first.

Bot commands

The command menu is the “/” button next to the input field in the chat with the bot:

  • /check — check the trackers now; the bot replies with a summary.
  • /watchlist — the list of titles, 8 per page, with a short state (🔔 awaiting a decision, ⬇️ downloading, ✅ in Plex — together with watched and deleted, 🔎 searching… or not suitable); “‹ ›” flip pages in the same message.
  • /status — Vartovyi status: titles, the last and the next check, free space.

A title button in /watchlist opens its card: the state and, for a show, a line per season (“S2 · 8/10 in Plex · 2 on trackers · ⬇️ 1 downloading”). 🔎 Search now searches for the title on all trackers, like on the title page (once per 5 min). 📥 Download season (for a movie — 📥 Download) lets you pick a season (“S1 ✅” — in Plex or watched and deleted, “S3 · 2 releases”), then up to 5 known releases, best first (“Toloka · 1080p WEB-DL · 12.3 GB · S02E01–E10”), and ⬇️ N buttons: the release is added to the torrent client with the same checks as on the site (space, title folder), and the result appears in the same message. No releases — “No releases with season N found yet” and 🔎 Search now. Releases already downloaded are marked “✅ downloaded” and have no button; “‹ Back to the list” returns to the list. If a search takes longer than a minute, it continues in the background — open the card again a minute later.

4Torrent client

The program that will download torrents: Download Station, qBittorrent or Transmission. In the wizard (step 7) you choose it at the “Torrent client” step, and set two folders there: one for shows and one for movies.

The program that will download torrents. On Linux and Raspberry Pi it is qBittorrent, which starts together with Vartovyi at step 6.

qBittorrent is already included.

On Linux and Raspberry Pi compose.yml (step 6) already contains qBittorrent next to Vartovyi: nothing to install now. In the wizard choose qBittorrent; the address http://qbittorrent:8090 is filled in. The login is admin, the password is the one you set at step 6.

Downloads go to /srv/media/Series and /srv/media/Movies (you create them at step 5) — add these two folders to Plex libraries: Series to a “TV Shows” library, Movies to a “Movies” library. Plex on the host sees them under the same path. If Plex itself runs in Docker, mount /srv/media into its container under the same path too.

Plex on another machine (another server, a NAS, a computer) doesn’t see /srv/media by itself. Share the media folder over the network (SMB with Samba, or NFS), mount or open the share on the Plex machine and add its Series and Movies folders to the libraries. The library path then differs from /srv/media, so the wizard shows the Plex warning “No Plex library found” for these folders — that is expected: the downloads still appear in Plex.

Already have qBittorrent or Transmission? Remove the qbittorrent service from compose.yml and enter the address of your client in the wizard (http://<NAS_IP>:<port>); the folders are paths as your client sees them. How to prepare each client is below.

If you don’t know what to choose, take Download Station: it is a Synology package and needs nothing but a DSM user. qBittorrent or Transmission make sense if you already use them.

Destination folders must be the same ones Plex scans. Then downloaded episodes appear in the library, and Vartovyi won’t notify about them again. Inside them Vartovyi creates a separate folder for each title (Title folders).

Download Station

A separate DSM user under which Vartovyi will add torrents.

  1. Control Panel → User & Group → Create, a name, for example, vartovyi.
  2. The Permissions tab: for the shared folder with videos (for example, video) — “Read/Write”.
  3. The Applications tab: for Download Station and File Station — “Allow”. File Station is needed to create a folder for each title; without it releases go to the root of the folder, and “Status” shows a warning.
  4. Don’t turn on two-factor authentication for this user, otherwise the API cannot sign in.

Destination folders are given relative to the root of the shared folders, without /volume1. If shows live in /volume1/video/Series, write video/Series in the wizard.

The DSM address is http://<NAS_IP>:5000. The HTTPS address :5001 with Synology’s default self-signed certificate won’t be accepted from the container. If HTTP-to-HTTPS redirection is on in Control Panel → Network → DSM Settings, turn it off or install a trusted certificate.

qBittorrent

  1. Turn on the Web UI in qBittorrent: Options → Web UI, the “Web User Interface (Remote control)” checkbox.
  2. Look up the port there (in the linuxserver Docker image — the WEBUI_PORT variable, 8090 in the example below) and set a login and password. You will enter them in the wizard.
  3. The address for the wizard: http://<NAS_IP>:<port>, for example http://<NAS_IP>:8090.

Folders are given the way qBittorrent itself sees them: if it runs in Docker — the path inside its container, for example /downloads/Series, not /volume1/…. qBittorrent can’t check whether such folders exist, so the wizard shows “this client cannot check folders”: see that they exist in qBittorrent’s saving settings. Leave the torrent content layout “Original” or “Create subfolder” (not “Don’t create subfolder”).

After a wrong login or password Vartovyi doesn’t try to sign in again for 15 minutes: after a few failed attempts qBittorrent bans the IP and may ban your browser too if the IP is the same.

Transmission

  1. RPC address: http://<NAS_IP>:9091/transmission/rpc. Port 9091 is the default; if you changed it, enter yours.
  2. Transmission only lets addresses from rpc-whitelist into RPC. Either add the home network and Docker subnets there (for example, 192.168.1.*,172.*.*.*), or turn the whitelist off ("rpc-whitelist-enabled": false) and set an RPC login and password (rpc-authentication-required, rpc-username, rpc-password). Edit Transmission’s settings.json while it is stopped: on exit it overwrites the file.
  3. Enter the login and password in the wizard only if they are set in Transmission, otherwise leave the fields empty.

Folders — the way Transmission sees them, for example /downloads/Series. The wizard checks that they exist.

qBittorrent in Docker next to Vartovyi

qBittorrent from the linuxserver image is a separate project in Container Manager (name qbittorrent, path docker/qbittorrent), created the same way as in step 6; the Vartovyi compose doesn’t change. The shared folder with videos /volume1/video is mounted in qBittorrent as /downloads, and Plex sees the same folder. In the wizard you then enter the address http://<NAS_IP>:8090 and the folders /downloads/Series and /downloads/Movies.

services:
  qbittorrent:
    image: lscr.io/linuxserver/qbittorrent:latest
    container_name: qbittorrent
    restart: unless-stopped
    environment:
      - PUID=1026        # uid of a user with rights to the video folder (id <user> over SSH)
      - PGID=100
      - TZ=Europe/Kyiv
      - WEBUI_PORT=8090
    ports:
      - "8090:8090"      # Web UI
      - "6881:6881"
      - "6881:6881/udp"
    volumes:
      - /volume1/docker/qbittorrent/config:/config
      - /volume1/video:/downloads   # the same folder Plex scans

Create the folders docker/qbittorrent/config and video/Series, video/Movies in File Station beforehand. On first start the linuxserver image writes a temporary password for the admin user to the qbittorrent container log: sign in to the Web UI with it and set your own password in Options → Web UI.

The Plex warning. The wizard compares the folders with the Plex libraries by path. For /downloads/Series it often finds no match, because Plex sees the same files as /volume1/video/Series, and says “No Plex library found”. If the folder really is in a Plex library, this warning can be ignored. To avoid it, mount the folder into Plex (if it runs in Docker too) under the same path as in qBittorrent.

Free space

Free space is shown in the release message, checked before downloading (if there isn’t enough, “Download” won’t add the task), it drives the 💾 low-space warning and the “Free space” card on the “Status” page. In the wizard you choose the source at the “Free space” step:

SourceWhen to use
Synology via DSM (synology)For Download Station: free space of the volume with the shared folder. With another client it usually gives “space unknown”: the path /downloads/Series doesn’t match any DSM shared folder.
The torrent client itself (client)For qBittorrent and Transmission. Transmission reports space for each folder separately, qBittorrent — one number for the disk of its default save folder. For Download Station it is the same as “Synology via DSM”.
Folder in the Vartovyi container (path)When the client doesn’t report space or reports it inaccurately: Vartovyi itself looks at the disk space of a mounted folder.
Don’t show (none)Space is not shown anywhere, downloads are not blocked for lack of space, there are no 💾 warnings. The “Free space” card says “not configured”.

On Linux and Raspberry Pi choose Folder in the Vartovyi container with the path /srv/media: compose.yml already mounts the media folder into Vartovyi under the same path (read-only), and the wizard suggests it.

For “Folder in the Vartovyi container” mount a folder from the same disk the downloads go to into the Vartovyi container, and enter its path in the container (here /media) in the wizard. Read-only is enough:

    volumes:
      - /volume1/docker/vartovyi/data:/data
      - /volume1/docker/vartovyi/config:/config
      - /volume1/video:/media:ro

In short: Download Station — “Synology via DSM”; qBittorrent or Transmission — “The torrent client itself”, and if the space is unknown, “Folder in the Vartovyi container”.

5Folders on the NASFolders

Two folders for data and settings, writable by the container.

The project folder for Vartovyi and the media folder for downloads, both writable by uid 1000.

In File Station → docker create the folder vartovyi, and inside it data and config:

/volume1/docker/vartovyi/
  data/     database, torrent and poster cache, tracker sessions
  config/   settings.json and quality.yaml — the wizard creates them

If the docker shared folder is not on volume1, replace the volume number in all paths (the “Volume” field in “Your details”). The path is shown in File Station → right-click the folder → Properties.

Write permissions. The container runs as the user with uid 1000, not as your DSM user, so permissions from File Station won’t help. Choose one option:

Option A · recommendedOver SSH
  1. Control Panel → Terminal & SNMP → “Enable SSH service”.
  2. On the computer: ssh <DSM_admin>@<NAS_IP>, the DSM password. The user must be an administrator.
  3. Run the command below, then SSH can be turned off.
sudo chown -R 1000:1000 /volume1/docker/vartovyi/data /volume1/docker/vartovyi/config
Option B · no SSHRun as root

At step 6 uncomment the line user: "0:0" in the compose file. The container will be able to write to any folder. Simpler, but less isolation.

Two folders, both can be changed in “Your details”:

  • The project folder ~/vartovyi — compose.yml and the container data next to it: data (database, torrent and poster cache, tracker sessions), config (settings, the wizard creates them) and qbittorrent (qBittorrent settings).
  • The media folder /srv/media — downloaded shows (Series) and movies (Movies); Plex scans it.
mkdir -p ~/vartovyi/data ~/vartovyi/config ~/vartovyi/qbittorrent
cd ~/vartovyi
sudo mkdir -p /srv/media/Series /srv/media/Movies
sudo chown -R 1000:1000 /srv/media

The project folder outside your home (for example /mnt/ssd/vartovyi): there mkdir without sudo fails with “Permission denied”. Create the folder first and make it yours, then run the commands above:

sudo mkdir -p ~/vartovyi && sudo chown $USER: ~/vartovyi
The media folder must be writable by uid 1000. qBittorrent and Vartovyi run in their containers as the user with uid 1000, not as root. A folder created with sudo belongs to root, and then torrents stop with “Permission denied” or hang at 0%. That is why sudo chown -R 1000:1000 /srv/media above is required — run it again whenever you create folders there with sudo or move the media to another disk.

The project folder. The containers run as uid 1000. id -u shows yours: on Raspberry Pi OS and most distributions the first user is 1000 already, then the folders in ~/vartovyi created above need nothing. Create data, config and qbittorrent before the first start, as above: otherwise Docker creates them as root, and Vartovyi can’t write to them. If id -u prints another number, give these three folders to uid 1000 (only them: the project folder itself stays yours, so you can still edit compose.yml, .env and Caddyfile):

sudo chown -R 1000:1000 ~/vartovyi/data ~/vartovyi/config ~/vartovyi/qbittorrent

Another media folder (for example an SSD at /mnt/ssd/media): create a .env file next to compose.yml with the line MEDIA_DIR=/mnt/ssd/media, enter this path in “Your details” and use it everywhere instead of /srv/media:

echo "MEDIA_DIR=/mnt/ssd/media" >> ~/vartovyi/.env

A project with one container. The settings are entered later, in the browser.

Three containers from one file: Vartovyi, qBittorrent and Watchtower for updates. The settings are entered later, in the browser.

Get the compose file

Download compose.linux.yml into the project folder under the name compose.yml: Compose finds this name by itself, so the commands below need no -f.

cd ~/vartovyi
curl -fsSL https://raw.githubusercontent.com/SorochanRoman/vartovyi-install/HEAD/compose.linux.yml -o compose.yml

Or create the file by hand with this content: nano compose.yml, paste the text, save with Ctrl+O and Enter, exit with Ctrl+X.

# Vartovyi on Docker for Linux (mini PC, server, Raspberry Pi with a 64-bit OS).
# Save as compose.yml next to a .env (optional) and run: docker compose up -d
# Guide: http://<server IP>:8080/guide
# Media folder: /srv/media by default; another one — put MEDIA_DIR=/path/to/media into a .env file next to this file.
services:
  vartovyi:
    image: ghcr.io/sorochanroman/vartovyi:latest
    pull_policy: always
    container_name: vartovyi
    restart: unless-stopped
    environment:
      - TZ=${TZ:-Europe/Kyiv}
    labels:
      # automatic updates (watchtower below) apply only to containers with this label
      - com.centurylinklabs.watchtower.enable=true
    ports:
      - "8080:8080"
    volumes:
      - ./data:/data
      - ./config:/config
      # read-only, only to count free space; the same path as on the host, so Plex paths match
      - ${MEDIA_DIR:-/srv/media}:${MEDIA_DIR:-/srv/media}:ro

  qbittorrent:
    image: lscr.io/linuxserver/qbittorrent:latest
    container_name: qbittorrent
    restart: unless-stopped
    environment:
      - PUID=1000
      - PGID=1000
      - TZ=${TZ:-Europe/Kyiv}
      - WEBUI_PORT=8090
      # group-writable files: a Plex on the host in the same group (1000) can delete watched episodes
      - UMASK=002
    ports:
      # web interface; first sign-in: user admin, temporary password in `docker logs qbittorrent`
      - "8090:8090"
      - "6881:6881"
      - "6881:6881/udp"
    volumes:
      - ./qbittorrent:/config
      - ${MEDIA_DIR:-/srv/media}:${MEDIA_DIR:-/srv/media}

  # Every night at 04:00 checks for a new vartovyi:latest image and restarts the container.
  watchtower:
    image: nickfedor/watchtower:latest
    container_name: vartovyi-watchtower
    restart: unless-stopped
    environment:
      - TZ=${TZ:-Europe/Kyiv}
      - WATCHTOWER_LABEL_ENABLE=true
      - WATCHTOWER_SCHEDULE=0 0 4 * * *
      - WATCHTOWER_CLEANUP=true
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock

Port 8080 is already taken on the server? Change only the left number in "8080:8080", for example "8081:8080", and enter it in “Your details”.

Start

cd ~/vartovyi
docker compose up -d
docker compose ps

The first start downloads the images: a few minutes, on a Raspberry Pi longer. ps must show all three containers — vartovyi, qbittorrent and vartovyi-watchtower — as “running” (“Up”). Run docker compose commands from ~/vartovyi: Compose looks for the file in the current folder.

qBittorrent password

On first start qBittorrent creates the user admin with a temporary password and prints it to its log:

docker logs qbittorrent 2>&1 | grep -i password
  1. Open http://<NAS_IP>:8090 and sign in as admin with this password.
  2. Tools → Options → Web UI, the “Authentication” block: set a permanent password and press “Save” at the bottom. You will enter admin and this password in the wizard (step 7).
  3. Optionally, on the “Downloads” tab set “Default Save Path” to /srv/media: then torrents you add by hand also land in the media folder.
Don’t open these ports to the internet. Forward neither 8080 nor 8090 from the router: from outside — only over HTTPS (step 13). Port 6881 is for torrent peers; forwarding it is optional and only speeds up downloads.

A minute or two after the start the container state becomes “healthy” (in Container Manager — “Healthy”in docker compose ps — (healthy)): the image calls /healthz every minute. “unhealthy” means the web server doesn’t answer — look at the log.

7Setup wizard

While the settings are incomplete, the service works only as the wizard page. The wizard checks each step with a live request.

  1. Open http://<NAS_IP>:8080, the service goes to http://<NAS_IP>:8080/setup by itself.
  2. Platform is the first step: Synology NAS, Docker on Linux or Raspberry Pi. It only sets the defaults in the next steps and the part of this Guide you see; you can change it later.
  3. Web interface password is the second step. At home no code is needed; from outside the home network the wizard first asks for the code from the container log (Container Manager → Container → vartovyi → Logdocker logs vartovyi, the line “Password setup code: 1234-5678”). The password is at least 8 characters; it is needed to sign in from outside (Access and password).
  4. Then go through the steps: Plex, Toloka, Telegram, Torrent client, Free space, Quality rules, Finish. On each, fill in the fields and press “Check”. “Next” becomes active after a success. The draft is saved, you can close the page and come back.
  5. Telegram: the check sends the test message “Vartovyi connected ✅”. If it didn’t arrive, press Start in the bot and check again.
  6. Torrent client: choose Download Station, qBittorrent or Transmission and fill in the fields (step 4). Automatic updates (Watchtower)

compose.yml already contains Watchtower (the vartovyi-watchtower container): every night at 04:00 it checks for a new vartovyi:latest, pulls it and restarts Vartovyi. qBittorrent has no label and is not updated automatically. The version is shown in the log (docker logs vartovyi): the line vartovyi <version> started.

Stop the project (Project → vartovyi → Action → Stop), in the project YAML add a label to the vartovyi service and, at the end, the Watchtower service, then “Save” → “Build”. Every day at 04:00 it pulls the new :latest and restarts only the labeled containers.

    labels:                 # in the vartovyi service
      - com.centurylinklabs.watchtower.enable=true

  watchtower:               # at the end, at the level of vartovyi:
    image: nickfedor/watchtower:latest
    container_name: vartovyi-watchtower
    restart: unless-stopped
    environment:
      - TZ=Europe/Kyiv
      - WATCHTOWER_LABEL_ENABLE=true
      - WATCHTOWER_SCHEDULE=0 0 4 * * *
      - WATCHTOWER_CLEANUP=true
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock

The image: of the vartovyi service must be :latest with the line pull_policy: always (as in step 6), otherwise “Build” may start an old version from the cache. The version is shown in the log: the line vartovyi <version> started.

For Watchtower to report updates in Telegram, add the line - WATCHTOWER_NOTIFICATION_URL=telegram://<BOT_TOKEN>@telegram?chats=<CHAT_ID> to its environment: (the bot token and chat_id from step 3). The schedule 0 0 4 * * * means every day at 04:00 (seconds, minutes, hours, day, month, weekday). It uses nickfedor/watchtower, a maintained fork: the original containrrr/watchtower is no longer developed and doesn’t work with new Docker versions. Watchtower has access to /var/run/docker.sock, which is why it is a separate service, and Vartovyi itself has no such access. Test versions (with a hyphen in the number, like 0.2.0-rc.1) are published only under their own number, so Watchtower won’t install them.

HTTPS via the Synology reverse proxy (DSM 7)

You need a domain name. The simplest is a free Synology DDNS name: Control Panel → External Access → DDNS → Add, service provider Synology, a name like vartovyi-home.synology.me. Below in the examples — <DDNS-name>.

    • Custom headers (WebSocket) are not needed. “Save”.

    vartovyi.example.com {

  respond @outside 403
  reverse_proxy 127.0.0.1:8080
}
  3. Start Caddy from the same folder: 
    docker run -d --name caddy --restart unless-stopped --network host -v caddy_data:/data -v $PWD/Caddyfile:/etc/caddy/Caddyfile caddy:2

Add the domain to WEB_ALLOWED_HOSTS (Access and password): the line - WEB_ALLOWED_HOSTS=vartovyi.example.com in the environment: block of the vartovyi service in compose.yml, then cd ~/vartovyi && docker compose up -d. Password sign-in doesn’t turn Vartovyi into an internet service. Forward only port 80 for the certificate — never 443, 8080 or 8090: push works without it. Keep the remote_ip private_ranges lines in the Caddyfile.

Day to day

In short: what Vartovyi does after installation and where to find it in the app.

Home

Home (http://<NAS_IP>:8080/) (the first tab) gathers the daily things on one screen; “Media” with all the titles is at http://<NAS_IP>:8080/media. At the top is the attention strip, only about what is wrong right now: “🔔 N releases awaiting a decision”, a dependency that doesn’t work, “⏸ Toloka paused until 14:30”, “⚠️ Stalled: …”, “🗑 … watched”, “⬇️ N downloading”. Each card can be hidden with the × button — it comes back when its content changes. Past failures are on the “Errors” page. Below are the “Ready to watch” (unwatched in Plex), “Downloading now”, “Waiting for a decision”, “Release schedule” (episodes for 14 days and season premieres for about 3 months, from TMDB — step 11; the data is cached for 12 hours, so right after a start the block says “Loading dates from TMDB…” for a few seconds) and “Popular now” blocks. The page refreshes every minute; if one block fails to load (say, TMDB is unreachable), it shows its own error, and the rest works.

Unwatched. Every 30 minutes Vartovyi refreshes the Plex server library and remembers the watched episodes (only the token owner’s): a card in “Media” shows a “▶ 3” badge, and the “▶ Unwatched” filter keeps such titles. On the season grid watched episodes are dimmed, and updates arrive with a delay of up to 30 minutes.

Stalled downloads

A download is stalled when the client is downloading but there is no new data for downloads.stallHours hours (6 by default; queueing, file checking and pause don’t count), or the client reported a task error. A message “⚠️ Stalled: Title S01E01–E03 · no progress for 7 h” arrives with the 🔁 Replace and ⏳ Keep waiting buttons; the same buttons are on Home and on the title page. An error cleared with “Clear error” doesn’t count as stalled; when the download moves again or finishes, the stall is cleared by itself. The downloads.stallHours threshold (1–168) is set in quality.yaml; restart the container after changing it.

  • Replace takes a saved release of the same title with all the needed episodes (first an updated version of the same topic, then by tracker order and quality); if there is none, it searches the trackers once. The stalled task is removed from the client without deleting files: Download Station deletes the incomplete download, qBittorrent and Transmission keep partial files. The tracker search runs at most once every 12 hours per title and for at most 5 titles an hour; if several downloads stalled at once or it is a disk or folder error, Vartovyi doesn’t search the trackers — the problem is likely in the torrent client. The title history gets an entry about the replacement; if the replacement couldn’t be added, the stalled task goes back to the client.
  • Keep waiting — 24 hours without reminders; if the download still doesn’t move, Vartovyi reminds you again with a fresh choice of replacement.
  • Auto-replace with a ⭐ followed release. If the best replacement among the ⭐ Following releases of the same title has all the needed episodes and passes the quality rules, Vartovyi doesn’t ask: it replaces the download right away, the same way as Replace (the stalled task is removed without deleting files, the followed release goes to the same folder; if it can’t be added, the stalled task goes back to the client), and sends “🔁 Auto-replaced: Title S01E01–E03” with the old and the new release and the reason. A re-upload of a followed topic (new torrent) replaces it with the updated version the same way. At most one auto-replacement per download and at most 2 per 30 minutes overall; nothing happens during “Keep waiting”. A client error is replaced automatically only after it has lasted downloads.stallHours hours (before that — the usual offer). When the problem looks like the torrent client (several downloads stalled at once, a disk or folder error, the client didn’t answer) — only the offer. Right before removing the task Vartovyi checks the client once more: if the download moved, nothing changes. If the followed release couldn’t be added, “⚠️ Auto-replace failed” says whether the stalled download was put back (Download Station starts it from scratch) or is gone from the client — then with the Replace / Keep waiting buttons; an auto-replacement interrupted by a restart is rolled back at startup the same way. Other replacements are only offered. If a replacement appears later (the next tracker search finds it while the download is still stalled), a followed one replaces the download automatically, and any other one updates the existing “⚠️ Stalled” message — at most one new notification per stall. To turn it off: the “Auto-replace a stalled download with a ⭐ followed release” switch on “Status” or downloads.autoReplaceFollowed: false.
  • The title page also has “🗑 Remove from client” and “🔄 Refresh torrent and re-download” (both with confirmation). “Remove from client” removes the task without deleting files (Download Station deletes the incomplete download), and the release can be downloaded again. “Refresh torrent” fetches the topic’s torrent from the tracker again: if the topic was re-uploaded, the new torrent goes to the same folder as a new task of the same download; if the torrent is the same — “The torrent on the tracker hasn’t changed”, and “↻ Restart task” appears. Vartovyi doesn’t go to a tracker paused after a failure; the same release can be refreshed again no sooner than in 3 minutes.

Delete watched

When a season is fully watched in Plex, Vartovyi offers to free up space — nothing is deleted without your “yes”: “🗑 Silo — season 2 watched (8 episodes, ≈ 34 GB)” with the 🗑 Delete / Keep buttons (in Telegram — also the confirmation “Yes, delete for good”). Only a season that is fully out is offered; the whole show — when it has ended (per TMDB) or was removed from the watchlist; movies — never. On the title page a watched season always has “🗑 Delete season”.

  • Needed in Plex: Settings → Library → Allow media deletion and the server owner’s token (step 1). Otherwise Vartovyi replies what exactly to turn on, and changes nothing.
  • Plex deletes the files of all copies of the season, Vartovyi removes only its own tasks of this season from the client and no longer searches for the deleted episodes. “Restore” on the title page removes the mark (the files are not restored).
  • At most 5 new offers per library refresh; after “Keep” the same season isn’t offered until new episodes appear in it. The confirmation in Telegram is valid for 10 minutes. If a show is in several libraries (for example, “TV” and “TV 4K”), a season counts as watched only when every copy is watched. While episodes of the season are still downloading, there are no offers. Small side files (subtitles, .nfo) and empty folders may remain.
  • Deleted in Plex itself? The next library refresh notices that the watched episodes are gone and marks them “watched and deleted” — Vartovyi will no longer offer to download them (“🗑 Season 2 deleted in Plex after watching…” in the title history). Unwatched episodes that disappeared are searched for as before; “Restore” removes the mark, and if the episodes appear in Plex again, it is removed by itself. The Plex trash is not deletion yet: the mark is set only when the episodes are gone from the trash too, and while watched episodes are in the trash, Vartovyi neither searches for nor offers them. If the library suddenly shrank (an unavailable disk, a Plex failure — over 30% of episodes or an empty section), nothing is marked this time and “Errors” shows a warning.
  • Security: anyone who opens the site can delete. In the “Sign-in: only from outside (HTTPS)” and “Sign-in: off” modes (WEB_LOGIN_MODE=off) that is anyone on the home network — choose “Sign-in: always” if needed (Access and password).

Plex on the host and “Delete watched”. Plex installed on the server itself (not in Docker) runs as the plex user, and the downloaded files belong to uid 1000 (qBittorrent). compose.yml makes them group-writable (UMASK=002): add plex to group 1000 and restart Plex, otherwise Plex can’t delete them. getent group 1000 must print a group; if it prints nothing, uid 1000 has no group with the same id — put the group of your user (id -gn) instead of $(getent group 1000 | cut -d: -f1). The first line makes the folders and files already in /srv/media group-writable too:

sudo chmod -R g+w /srv/media
sudo usermod -aG $(getent group 1000 | cut -d: -f1) plex
sudo systemctl restart plexmediaserver

Title folders and matching in Plex

New downloads go to the title folder with a hint for Plex: video/Series/House of the Dragon (2022) {tmdb-94997}. The name is the original one if it is in Latin letters, otherwise the one from the watchlist; without a TMDB id the hint is {tvdb-…} or {imdb-tt…}. The folder is remembered in the release: new episodes, “Download again” and “Replace” go there too. Download Station doesn’t create folders itself — Vartovyi does it via File Station as the same DSM user (the permission from step 4); without access the release goes to the root of the folder, and “Status” shows a warning. qBittorrent and Transmission create folders themselves. Existing files are not moved: releases downloaded to the root earlier stay there. To turn it off: the “A separate folder for each title” switch on “Status”, the checkbox in the wizard or downloads.perTitleFolder: false.

If Plex matched a download to a different title, Vartovyi fixes unambiguous cases by itself (“Fix match”, an entry in the title history), otherwise the title page shows a “Plex match” block with a “Fix in Plex” button and the reason (the item holds files of several titles, a release is spread over several items, the library uses the old Plex agent, an old release in the root of the folder) — check the item in Plex before pressing it. If the match is changed in Plex itself after the fix, Vartovyi leaves it alone. “Fix match” needs the server owner’s token, otherwise Plex answers 401 (an entry in “Errors”).

Exact and possible matches

An exact match (the same name and a matching year) gives a notification and the “Awaiting decision” status. A possible match (the year differs by 2–3 years) is saved without a notification — in the “Possible matches” section on the title page, where you can download or ignore it. For a show only a topic with a season mark is kept this way. On every search Vartovyi re-checks the saved releases without a decision: those that don’t match the title at all are ignored (“🔕 Doesn’t match the title: …” in Telegram), and exact and possible ones are marked anew.

Poster cache

Vartovyi keeps posters and backdrops in data/image-cache (up to 500 MB, the oldest are removed by themselves). To clear it, stop the project and delete this folder.

Access and password

At home (http://<NAS_IP>:8080) Vartovyi opens without a password; from outside — via the HTTPS proxy — only after sign-in. The Telegram bot and push work regardless of sign-in: the “Download” / “Ignore” buttons in push have their own one-time token.

Sign-in modes

On the Status (http://<NAS_IP>:8080/status) page, the “Access” block:

  • “Sign-in: only from outside (HTTPS)” — the default. No password only for a request from the home network: without proxy headers (X-Forwarded-For, X-Forwarded-Proto, X-Real-IP, Forwarded…), to the private IP of the server, localhost or a home name (without a dot, .local, .lan, .home, .home.arpa, .internal or from WEB_LOCAL_HOSTS), from a private address of a device that isn’t the Docker gateway or an address from WEB_TRUSTED_PROXIES. Tailscale / CGNAT and global IPv6 — with a password.
  • “Sign-in: always” — a password at home too.
  • “Sign-in: off” — no password from anywhere, including via the HTTPS proxy. The same with the WEB_LOGIN_MODE=off variable in compose (it overrides the setting — for when you can’t sign in). Choosing “off” on “Status” when a password exists requires entering it — even at home. If the reverse proxy is reachable from the internet, in this mode Vartovyi is open to everyone.

“Access” shows for the current request “Your address: … — home network, no sign-in needed” or “… — sign-in required (reason: …)”. If requests come straight from a public address (the port is open to the internet), “Access” shows a warning with the latest such address, and the “Errors” journal — “A request came straight from the internet”. If the server shows all home devices with the Docker gateway address (it happens on some DSM builds in a bridge network), Vartovyi safely falls back to always requiring sign-in — the same line shows the reason.

A proxy without X-Forwarded-For and port forwarding with SNAT look like the home network. nginx with a plain proxy_pass, stunnel, HAProxy mode tcp, frp, a tunnel, and also port forwarding on the router with address rewriting (SNAT, NAT loopback — the sender becomes the router’s LAN address) give anyone on the internet access without a password. For them choose “Sign-in: always” or add the proxy or router address to WEB_TRUSTED_PROXIES (comma-separated, subnets allowed). The DSM reverse proxy adds the headers — it is fine.Caddy adds the headers — it is fine.

Best of all, make your proxy add X-Forwarded-For and X-Forwarded-Proto (in nginx: proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme;). The session cookie is marked Secure only when the request came over HTTPS — directly or from a proxy with X-Forwarded-Proto: https; without this header sign-in works, but the cookie lacks the Secure mark.

Host names. WEB_ALLOWED_HOSTS — the names the site is opened by from outside (DDNS for HTTPS, step 13); WEB_LOCAL_HOSTS — your own domain you open Vartovyi by at home (split DNS), so it doesn’t ask for a password (don’t put the name Vartovyi is reachable by from outside there). The site API (/api/…) answers only requests to an IP address, localhost, a name without a dot, a home suffix (.local, .home.arpa, .internal, .lan, .home) or a name from WEB_ALLOWED_HOSTS (several names comma-separated) — this protects against DNS rebinding; otherwise pages open, but the data doesn’t load (403 “unknown server address”).

Password

A new Vartovyi asks for a password at the wizard’s Password step. At home you can create or change it on “Status” → “Access” without a code. From outside, while there is no password, any page opens “Create a password”: it needs the code from the log — Container Manager → Container → vartovyi → Logdocker logs vartovyi, the line “Password setup code: 1234-5678” (new after every restart; over SSH: sudo docker logs vartovyi 2>&1 | grep "setup code"). The line may appear in the log twice (as a plain line and as a JSON entry) — it is the same code; once the password is created, the code no longer works.

Sign-in is remembered for 30 days. The app from the iPhone icon has storage separate from Safari — sign in there separately. On “Status” → “Access” there is the list of sessions, “Log out” next to each, “Log out on all devices” and “Change password”. “Log out” is also in the top bar.

Forgot the password

  1. In compose.yml add - WEB_PASSWORD=new-password (at least 8 characters) to the environment: block of the vartovyi service and run cd ~/vartovyi && docker compose up -d. The password changes, all devices are signed out.
  2. Sign in with the new password, remove the line and run cd ~/vartovyi && docker compose up -d again — the password stays.
  1. Project → vartovyi → Action → Stop, add - WEB_PASSWORD=new-password (at least 8 characters) to environment:, “Build”. The password changes, all devices are signed out.
  2. Sign in with the new password, remove the line and “Build” again — the password stays.

While WEB_PASSWORD is set, “Status” shows a reminder to remove the variable, and the password can’t be changed in the web interface. The value is never shown or written to the log. If it matches the current password, the restart signs nobody out — use “Log out on all devices” for that.

Failed attempts

After every wrong password or code the next attempt from the same address is possible in 1, 2, 4, 8 … s, the delay doubles up to 15 min and resets after sign-in or a day without errors. The delay is per address (behind a proxy — from X-Forwarded-For), so someone else’s attempts don’t lock you out. Separately, after 50 failed attempts in an hour from any addresses, every sign-in from a new outside address is slowed down by a few seconds, but not rejected; addresses with a successful sign-in in the last 30 days and the home network are not slowed down. Every attempt is in the “Errors” journal as “Failed sign-in attempt”.

Never open port 8080 to the internet — neither by IPv4 forwarding nor over IPv6. From outside — only via the DSM reverse proxy over HTTPS (step 13); in the DSM firewall allow 8080 only for the home network.From outside — only over HTTPS via Caddy or Tailscale (step 13). At home anyone on your network (the guest Wi-Fi too) opens Vartovyi without a password — if that won’t do, choose “Sign-in: always”.

Log and diagnostics

The “Errors” page (Status → Problems in 24 h (http://<NAS_IP>:8080/errors)) shows all failures with their reasons: the source, how many times it repeated, when first and last, and the details. Identical failures within a day are grouped into one problem. Start there, and open the container log when you need the details of every request.

The log: Container Manager → Container → vartovyi → Logdocker logs vartovyi (live: docker logs -f --tail 100 vartovyi). Every network failure has a reason, for example Toloka tracker is unreachable: fetch failed: ENOTFOUND toloka.to or an http failed line with a reason field. During an outage only the first failure is a warning (identical repeats go to debug), and when the service answers again — an http recovered line. To see every request and every decision of the cycle, turn on the detailed log:

  1. In compose.yml add the line - LOG_LEVEL=debug to the environment: block of the vartovyi service and run cd ~/vartovyi && docker compose up -d.
  2. Wait for the next check (or /check in the bot) and look at the log: docker logs -f vartovyi.
  3. After the diagnostics remove the line and run cd ~/vartovyi && docker compose up -d again: in debug mode the log grows fast.

In this case create the config/quality.yaml file yourself:

quality:
  minResolution: 1080p          # 720p | 1080p | 2160p
  preferredResolution: 1080p    # which resolution to take first (default = minResolution)
  preferredSources: [WEB-DL, BluRay]   # order = source priority
  rejectSources: [CAMRip, TS, TC]
  requireUkrainianAudio: true
  notify: best                  # best | all

schedule:
  plexHours: 24                 # how often to sync the watchlist with the Plex cloud, hours (1–168)
  tolokaHours: 12               # how often to search the trackers for releases, hours (1–168)
  # plexTimes: ["04:00"]          # or sync Plex at the given times (HH:MM, comma-separated) — instead of plexHours
  # trackerTimes: ["07:00", "19:00"]   # or search the trackers at the given times — instead of tolokaHours

storage:
  minFreeGb: 50                 # free space warning threshold on the disk, GB

downloads:
  stallHours: 6                 # how many hours without progress make a “stalled download” (1–168)
  perTitleFolder: true          # a separate “Title (Year) {tmdb-id}” folder for each title (also a switch on “Status”)
  autoReplaceFollowed: true     # replace a stalled download with a ⭐ followed release automatically (also a switch on “Status”)

Schedule. Vartovyi wakes up every 30 minutes: it sends unsent messages and refreshes the Plex server library. It syncs the watchlist from the Plex cloud once every plexHours hours (24 by default), and searches the trackers for releases once every tolokaHours hours (12 by default); new titles from the watchlist are searched for right away. “Refresh” on “Media”, “Check now” or /check start everything immediately. Both intervals can also be changed on the “Status” page in the “Schedule” block — they apply right away and are saved to quality.yaml. The old intervalMinutes field no longer works and is ignored.

At given times. Instead of “every N hours” — plexTimes and trackerTimes: lists of HH:MM times (up to 24 values, no repeats), for example trackerTimes: ["07:00", "19:00"]. The time is the container’s local time, that is the TZ variable. If a time was missed (the server was off), there is one run after the start, not one per missed time. A manual run doesn’t shift the schedule: the next one is at the nearest given time. A run at a given time starts on time (within seconds), not at the next 30-minute step; the mode is set for each channel separately; the search pause after a tracker failure is then no longer than the shortest gap between the times.

Choosing a release. preferredSources is the order of sources (earlier = better), preferredResolution is the resolution to take first. notify: best (the default) — only the best release goes to Telegram, the rest stay on the title page; notify: all — a notification about each. Source names: BluRay, HDDVDRip, WEB-DLRip, WEB-DL, WEBRip, BDRip, HDTV, DVDRip, SATRip, HDRip, TVRip, CAMRip, TS, TC (case doesn’t matter; the same names work in rejectSources; HD-DVDRip is HDDVDRip). Sources not in the list come after the listed ones, an unknown one is last; higher resolutions come after preferredResolution. With equal source and resolution, the release already notified about wins, then the one with more new episodes, then the smaller one. The size in the message and the space check: if the release hasn’t been downloaded yet — the whole release; if an earlier version of it is already downloaded — only the new episodes. After changing quality.yaml by hand, restart the container.
